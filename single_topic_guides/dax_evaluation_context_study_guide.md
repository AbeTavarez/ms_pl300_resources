# PL-300 Exam Study Guide: DAX Evaluation Context

Evaluation context is the foundational set of rules governing how DAX expressions calculate results. Mastering evaluation context is critical for understanding DAX behavior and passing the **Microsoft Certified: Power BI Data Analyst Associate (PL-300)** exam.

---

## 1. The Three Types of DAX Context

### 1. Row Context
* **Definition:** The concept of the **"current row"**. It enables DAX to evaluate columns row-by-row as it iterates through a table.
* **Where it exists automatically:**
  * In **Calculated Columns**.
  * Inside **Iterating Functions** (e.g., `SUMX`, `AVERAGEX`, `FILTER`, `ADDCOLUMNS`).
* **Key Characteristic:** Row context **does not automatically filter other tables** or propagate across relationships. It simply instructs DAX to read values from a specific row in the current table.

### 2. Filter Context
* **Definition:** The set of active filters applied to the data model during evaluation. It determines which subset of rows from each table is visible to a calculation.
* **How it is created:**
  * User interactions on report pages (Slicers, Visual Filters, Page Filters, Report Filters, Cross-highlighting).
  * **Row-Level Security (RLS)** role definitions.
  * DAX expressions using `CALCULATE()` or `CALCULATETABLE()`.
* **Key Characteristic:** Filter context **propagates across active table relationships** (typically from the "one" side to the "many" side) to constrain visible rows across the model.

### 3. Query Context
* **Definition:** The macro-level evaluation environment generated by a visual on a report page.
* **How it works:** When a visual (e.g., a Matrix, Table, or Bar Chart) requests data, it constructs a query context that combines:
  * Rows, Columns, Legend, and Axis field placements in the visual.
  * All active report, page, and visual slicers/filters.
* **Key Characteristic:** Query context establishes the initial Filter Context for every individual data cell rendered within a visual.

## 3. Why Measures Require Aggregators (and Calculated Columns Do Not)

### In Calculated Columns
A calculated column evaluates inside an automatic **Row Context**. Because DAX evaluates the table one row at a time, a formula like:

```dax
LineTotal = Sales[Quantity] * Sales[UnitPrice]
```

knows *exactly* which single row value to extract. No aggregation is necessary because there is no ambiguity about which row is being referenced.

### In Measures
A measure operates purely within a **Filter Context**, where hundreds, thousands, or millions of rows may be visible simultaneously. 

If you attempt to write:

```dax
-- INVALID MEASURE SYNTAX
TotalUnitPrice = Sales[UnitPrice]
```

DAX returns an error:
> *"A single value for column 'UnitPrice' in table 'Sales' cannot be determined."*

Because multiple rows are selected by the current filter context (e.g., all sales in Year 2026), DAX requires an **Aggregator** (`SUM`, `AVERAGE`, `MIN`, `MAX`) or an **Iterator** (`SUMX`, `AVERAGEX`) to condense those multiple row values down into a single scalar result.

## 4. Writing DAX: How Context Applies to Functions

### A. Context Transition (Crucial Exam Concept)
Context transition occurs when an existing **Row Context is converted into an equivalent Filter Context**.

* **Trigger:** Calling `CALCULATE()` (or `CALCULATETABLE()`) inside a Row Context.
* **Implicit Transition:** Referencing a Measure inside a Calculated Column or Iterator automatically wraps the measure in an implicit `CALCULATE()`, triggering Context Transition.

```dax
-- Example inside a Calculated Column on the Customer table:
-- Implicit Context Transition filters the Sales table down to only rows matching the current Customer ID.
CustomerTotalSales = [Total Sales]
```

### B. Iterators (`SUMX`, `AVERAGEX`, `FILTER`)
Iterators accept a table expression, establish a **Row Context** over that table, and evaluate an expression for each row sequentially.

```dax
TotalRevenue = 
SUMX(
    Sales,
    Sales[Quantity] * Sales[UnitPrice]  -- Evaluated in Row Context per row, then aggregated
)
```

### C. Modifying Filter Context (`CALCULATE` + Filter Modifiers)
`CALCULATE` is the primary DAX function capable of modifying, clearing, or adding to the existing Filter Context.

```dax
-- ALL() removes filters on Product[Category] from the Filter Context
CategoryPercentOfTotal = 
DIVIDE(
    [Total Sales],
    CALCULATE(
        [Total Sales], 
        ALL(Product[Category])
    )
)
```

## 5. Sample PL-300 Practice Questions

### Question 1

**Scenario:** You create a calculated column in the `Customer` table using the formula `= [Total Sales]`, where `[Total Sales]` is defined as `SUM(Sales[Amount])`. What mechanism allows this calculated column to compute sales specific to each customer row?

A. Query Context  
B. Row-Level Security  
C. Context Transition  
D. Bidirectional Cross-Filtering  

* **Correct Answer:** **C**  
* **Explanation:** Referencing a measure (`[Total Sales]`) inside a calculated column invokes an implicit `CALCULATE()`, which converts the row context of the `Customer` table into an equivalent filter context filtering the `Sales` table.

---

### Question 2

**Scenario:** A report contains a Matrix visual displaying Sales by Product Category. A user selects "2026" in a Year slicer. Which context determines the sales figure rendered in the Matrix cell for the "Electronics" category?

A. Row Context only  
B. Filter Context created by the slicer selection ("2026") and the Matrix row ("Electronics")  
C. Query Context containing only the Matrix row label  
D. Row Context converted into Query Context  

* **Correct Answer:** **B**  
* **Explanation:** Visual cell values are evaluated under a Filter Context generated by combined report filters (slicers, page filters) and visual groupings (Matrix rows/columns).
