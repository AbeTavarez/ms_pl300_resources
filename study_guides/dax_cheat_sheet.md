# Microsoft Power BI PL-300 Exam: DAX Functions Cheat Sheet

This cheat sheet summarizes the core Data Analysis Expressions (DAX) functions, concepts, and patterns frequently tested on the **Microsoft PL-300: Power BI Data Analyst** certification exam.

---

## 1. Context Modification & Filter Controls (Highest Priority)
These functions modify or override the report's filter context, which is the single most heavily tested area in the PL-300 exam.

| Function | Syntax | Primary Use Case & Exam Distinction |
| :--- | :--- | :--- |
| **`CALCULATE`** | `CALCULATE(<expr>, <filter1>, ...)` | Evaluates an expression in a modified filter context. Converts row context to filter context (**Context Transition**). |
| **`ALL`** | `ALL(Table[Column] or Table)` | Removes filters from specified columns or tables to calculate grand totals or percentages of total. |
| **`ALLEXCEPT`** | `ALLEXCEPT(Table, Table[Col1], ...)` | Removes all filters from a table **except** on the specified columns. Useful for regional/category sub-totals. |
| **`ALLSELECTED`** | `ALLSELECTED(Table[Column])` | Ignores inner visual filters but respects explicit slicers/filters set by the user on the canvas. |
| **`FILTER`** | `FILTER(Table, Condition)` | Returns a table. Used inside `CALCULATE` for complex conditions (e.g., comparing measure values to constants or other measures). |
| **`KEEPFILTERS`** | `KEEPFILTERS(<filter_expr>)` | Modifies how filters are applied in `CALCULATE` by **intersecting** existing filters instead of overriding them. |
| **`USERELATIONSHIP`** | `USERELATIONSHIP(Col1, Col2)` | Activates an **inactive** relationship between two tables for the duration of the calculation. |

## 2. Time Intelligence Functions
These require a dedicated Date Table marked as a **Date Table** in Power BI with contiguous dates.

| Function | Syntax | Primary Use Case & Exam Distinction |
| :--- | :--- | :--- |
| **`TOTALYTD`** / **`MTD`** | `TOTALYTD(<expr>, 'Date'[Date])` | Evaluates year-to-date or month-to-date totals. Syntactic sugar for `CALCULATE` + `DATESYTD`. |
| **`SAMEPERIODLASTYEAR`** | `SAMEPERIODLASTYEAR('Date'[Date])` | Shifts the date context back by exactly 1 year. Used for year-over-year comparisons. |
| **`DATEADD`** | `DATEADD('Date'[Date], Number, Interval)` | Shifts dates by a specified interval (`DAY`, `MONTH`, `QUARTER`, `YEAR`). More flexible than `SAMEPERIODLASTYEAR`. |
| **`PARALLELPERIOD`** | `PARALLELPERIOD('Date'[Date], Number, Interval)` | Returns a table of dates for the full period (`MONTH`, `QUARTER`, `YEAR`), regardless of current date selection details. |
| **`DATESBETWEEN`** | `DATESBETWEEN('Date'[Date], Start, End)` | Returns dates within a custom date range. Useful for dynamic rolling metrics (e.g., last 30 days). |

## 3. Iterators (X-Functions)
Iterator functions loop through a table line-by-line, creating a **row context** before aggregating the result.

| Function | Syntax | Primary Use Case & Exam Distinction |
| :--- | :--- | :--- |
| **`SUMX`** | `SUMX(Table, Expression)` | Calculates row-by-row before summing (e.g., `SUMX(Sales, Sales[Qty] * Sales[Price])`). |
| **`AVERAGEX`** | `AVERAGEX(Table, Expression)` | Calculates an expression for each row, then takes the average of those results. |
| **`RANKX`** | `RANKX(Table, Expression, [Value], [Order], [Ties])` | Ranks items dynamically based on a measure expression. |

---

## 4. Logical & Relationship Functions

| Function | Syntax | Primary Use Case & Exam Distinction |
| :--- | :--- | :--- |
| **`SWITCH`** | `SWITCH(TRUE(), Cond1, Res1, Cond2, Res2, ...)` | Replaces nested `IF` statements. Using `SWITCH(TRUE(), ...)` allows evaluating multiple dynamic conditions cleanly. |
| **`RELATED`** | `RELATED(Column)` | Fetches a value from the "One" side of a 1-to-Many relationship into the "Many" side (requires existing row context). |
| **`RELATEDTABLE`** | `RELATEDTABLE(Table)` | Returns a table of related rows from the "Many" side to the "One" side. |
| **`COALESCE`** | `COALESCE(Expr1, Expr2, ...)` | Returns the first non-BLANK expression. Efficient way to replace `BLANK()` with defaults like `0`. |

---

## 5. Table Manipulation Functions
Exam questions often test which function generates calculated tables, summary tables, or temporary evaluation tables.

| Function | Syntax | Primary Use Case & Exam Distinction |
| :--- | :--- | :--- |
| **`VALUES`** | `VALUES(Table[Column] or Table)` | Returns a single-column table of unique values, respecting current filter context (includes `BLANK()` row if present due to RI violation). |
| **`DISTINCT`** | `DISTINCT(Table[Column] or Table)` | Similar to `VALUES`, but does not include the unknown `BLANK()` row generated by referential integrity violations. |
| **`CALENDARAUTO`** | `CALENDARAUTO([fiscal_year_end_month])` | Generates a single-column date table automatically based on all date columns in the data model. |
| **`SUMMARIZE`** | `SUMMARIZE(Table, GroupBy_Col1, "Name", Agg)` | Groups data by specified columns and returns summary aggregates. |
| **`ADDCOLUMNS`** | `ADDCOLUMNS(Table, "Name", Expression)` | Adds calculated columns to an existing table expression. Best practice is pairing `ADDCOLUMNS` with `SUMMARIZE`. |

## 6. Security & Information Functions

| Function | Syntax | Primary Use Case & Exam Distinction |
| :--- | :--- | :--- |
| **`USERPRINCIPALNAME`** | `USERPRINCIPALNAME()` | Returns the user's email address (`user@domain.com`) in Power BI Service. Primary choice for Row-Level Security (RLS) dynamic roles. |
| **`USERNAME`** | `USERNAME()` | Returns `Domain\User` in Power BI Desktop or GUID/Email in Service. Prefer `USERPRINCIPALNAME` for RLS. |
| **`ISFILTERED`** | `ISFILTERED(Column)` | Returns `TRUE` if the specified column is directly filtered. |
| **`HASONEVALUE`** | `HASONEVALUE(Column)` | Returns `TRUE` when the column has been filtered down to a single distinct value (e.g., checking if a row in a visual is a total row or detail row). |

## High-Yield Exam Pitfalls

1. **`CALCULATE` Overwriting vs. Merging Filters:** By default, passing a basic filter argument into `CALCULATE` (e.g., `CALCULATE([Sales], Region[Country] = "USA")`) **overwrites** existing filters on `Region[Country]`. Wrap it with `KEEPFILTERS` if you want to intersect/keep existing filters instead.
2. **Implicit vs. Explicit Measures:** Explicit DAX measures should always be used over implicit measures for performance, maintainability, and Row-Level Security scenarios.
3. **`COUNT` vs `COUNTROWS`:** `COUNT` operates on a specific column and skips blanks. `COUNTROWS` counts all rows in a given table (including blank rows) and is computationally more efficient for total row counts.
